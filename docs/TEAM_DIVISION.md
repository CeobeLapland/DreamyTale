# 团队分工与协作边界

本文档约定 DreamyTale 的三人协作方式、职责边界、目录归属和交接接口。项目负责人可根据实际姓名替换成员编号，但职责和决策边界保持不变。

## 1. 项目目标

交付一本绘本的完整闭环：

```text
绘本 PDF/图片
→ 页面与脚本解析
→ OCR/VLM 内容理解
→ 故事与分镜
→ 视频和配音
→ 网页播放
→ 点击、查找、高亮、语音问答
→ 评测结果与演示视频
```

系统必须支持第二本同级别绘本，不得把页面内容、点击坐标或问答答案写死。

## 2. 角色与决策权

### B：项目负责人、生成链路负责人

B 是项目最终验收人，负责：

- 选择 OCR/VLM、故事模型、文生视频和 TTS 方案。
- 负责故事改编、分镜、视觉一致性、视频合成和生成质量。
- 决定视频生成失败时的降级策略。
- 组织每日联调和最终演示彩排。
- 对“是否继续优化”与“何时冻结功能”作最终决定。

默认目录：

```text
pipeline/       生成链路、模型适配、分镜与视频合成
prompts/        可版本化的提示词和模型配置
```

### A：后端与平台负责人

A 负责把 B 的生成能力和 C 的交互需求落到稳定服务中：

- 素材导入、单书数据包、页面与脚本解析。
- 任务创建、排队、进度、重试、超时、缓存和失败恢复。
- OCR/VLM/ASR/TTS/视频模型的服务端适配器。
- 书籍、场景、文字、热区和问答数据接口。
- 评测指标收集和日志。
- 本地一键启动与现场环境恢复。

默认目录：

```text
backend/        后端服务、数据导入、模型适配和任务系统
contracts/      与 B、C 共同维护的数据契约
```

### C：前端、交互与评测负责人

C 负责用户实际看到和操作的流程：

- 网页/平板阅读器和视频播放器。
- 上传、拍照、播放、暂停、继续和进度展示。
- 点击热区、对象信息卡、文字查找与高亮。
- 语音录制、ASR/TTS 交互、对话历史和错误提示。
- Query 音频评测工具、结果记录和演示视频录制。

C 不得直接调用模型 SDK，所有模型能力通过 A 提供的后端接口访问。

默认目录：

```text
frontend/       网页或平板 Demo
evaluation/     评测脚本、结果汇总和演示素材
```

## 3. 目录所有权

| 目录/文件 | 主责 | 规则 |
| --- | --- | --- |
| `backend/` | A | B、C 需要改动时先与 A 对齐接口 |
| `pipeline/` | B | 前端不直接调用，由后端封装 |
| `prompts/` | B | 变更必须记录版本和适用模型 |
| `frontend/` | C | 只消费已约定的 API 数据 |
| `evaluation/` | C | 评测输入和结果不得包含未脱敏素材 |
| `contracts/` | A、B、C | 破坏性修改必须三人确认 |
| `docs/` | 全员 | 按文档主题维护，不覆盖他人内容 |
| `temp/` | 全员 | 本地临时数据和生成结果，不进入 Git |
| `abandoned/` | 全员 | 已废弃实验，不参与构建 |

组委会 PDF、WAV、ZIP 和评测原始数据不得提交到 Git。仓库公开可读，只能提交代码、配置、文档和脱敏后的示例数据。

## 4. 接口交接

### B 交给 A

B 的生成能力必须封装为可调用函数或服务，输入和输出遵守 `docs/DATA_CONTRACT.md`：

```text
BookPackage + Page + ScriptStep
→ StoryPlan
→ ScenePlan
→ VideoSegment
→ BookGenerationResult
```

B 负责生成质量，A 负责把生成函数包装成可重试、可监控的后端任务。

### A 交给 C

A 提供稳定的 HTTP 接口和事件格式：

```text
POST /api/books/ingest
GET  /api/books
GET  /api/books/{book_id}
POST /api/books/{book_id}/generate
GET  /api/jobs/{job_id}
POST /api/qa
```

接口字段以 `docs/DATA_CONTRACT.md` 为准。A 不要求 C 读取后端内部文件。

### C 交给全组

C 提供：

- 可运行的网页 Demo。
- 前端对数据结构缺口的反馈。
- Query 评测结果。
- 交互版和非交互版演示视频。

## 5. 分支与合并规则

- 不直接修改 `origin/main`。
- 分支命名：

```text
feature/backend-*
feature/pipeline-*
feature/frontend-*
fix/<component>-*
```

- 每次开始工作前先检查远端和工作区。
- 至少每三次团队反馈或连续工作轮次，检查一次 `origin/main`。
- 不修改其他成员正在负责的目录；确需修改时先说明原因和影响。
- 合并前必须至少完成：

```text
git status
相关单元测试
接口样例或页面自测
```

## 6. 每日协作

建议每天固定两次同步：

- 中午：确认接口、阻塞和素材问题。
- 晚上：合并可运行版本，更新演示进度。

每日必须回答：

1. 今天哪个用户流程已经真实跑通？
2. 哪个外部 API 或数据依赖仍不确定？
3. 明天最可能阻塞谁？
4. 是否需要砍功能？

## 7. 完成定义

一项工作只有同时满足以下条件才算完成：

- 代码已合入对应功能分支。
- 输入、输出和错误状态符合数据契约。
- 有可复现的启动或调用命令。
- 至少完成一次真实数据或集成测试。
- 对使用者说明已知限制和降级行为。

## 8. 当前关键路径

当前优先顺序：

1. A 完成单书数据包导入和统一 API。
2. B 在单书数据包上完成故事、分镜和一段视频。
3. C 使用 Mock 数据完成播放器与交互壳。
4. 三人基于同一本 `zh-01` 做第一次端到端联调。
5. 第 3 天结束仍依赖人工改中间文件时，暂停新增功能，优先修复自动化链路。
