# 0003 · 328 条是样本，不是规格

日期：2026-11-15

## 背景

命题组给了六本绘本、328 条交互脚本。它们摆在那里，太容易照着做——每条 query 配一张卡，逐条打通，正确率很好看。但这样做出来的东西，离开这六本就一文不值，评委只要问一句"换一本书行不行"就穿帮。

而且这本来就不是我们想做的产品。"把纸书变成可问答的界面"如果是真的，就必须对任何一本书成立。

## 决定

**结构上把"能力"和"知识"分开。**

- **能力层**只认契约不认书。六类交互（control/seek/search/highlight/touch/qa）是对纸书这种媒介的通用能力，代码里不许出现任何书名、页号、角色名。
- **知识层**每本书独立生成，来源可以是自动抽取，也可以是人工标注。**人工标注是可选的增强，不是必需路径。**

检验方法很简单：**拿一本没见过的新书跑一遍，代码一行不改，系统要能开口说话。** 哪怕回答质量差，也要能走完流程、给出引导档。

配套四条兜底，缺一条就不叫通用：

1. **未知书** → 自动冷启动（拆页 → OCR/VLM → 事实 → 时间轴骨架）
2. **未知意图** → 走 `other` 通道接通用对话，**不是回复"我做不到"**
3. **未知物体** → 开放词表检测，不限于标注过的清单
4. **未知语言** → 检测后同语言回

## 代价

- 冷启动管线要真做，短期比"写死六本"慢一周
- 兜底路径会拉低精确率。有些问题本来该拒答，通用通道会硬答。所以要用分档阈值控制，宁可多说一句"我猜你是想问…"
- 知识层自动产出的东西质量不如人工，需要 provenance 字段区分，答辩时要能说清哪条是精标、哪条是自动

## 备选

**只做这六本。** 快，正确率高，但交付物比赛后即废，且违背做这件事的初衷。

## 什么时候该重新考虑

不需要重新考虑。如果哪天发现"为了通用多花了三周但一页没跑通"，那是排期问题，不是方向问题——降级做法是先只把冷启动跑通到"能出页面和事实"，把质量优化推迟。
